# 평가 설계 구현 가이드

- 작성일: 2026-10-10
- 대상: 평가 담당 팀원 (설계안 13.3의 모델 실행·출력 정규화·통계·재현 기록 역할)
- 기준 문서: [최종설계안.md](../최종설계안.md) v2.0 8~12장, [AGENTS.md](../AGENTS.md)
- 짝 문서: [말뭉치_활용_구현가이드.md](말뭉치_활용_구현가이드.md). 이 문서의 입력 형식(`items_v1.jsonl`)은 그쪽 6절에서 정의한다.
- 상태: 모델 ID, 프롬프트 문구, 실제 실행 결과는 아직 없다. 이 문서는 코드와 기록 형식을 먼저 준비하기 위한 지침이다.

## 0. 전제와 규칙

- Python 3.10 이상, 표준 라이브러리만 사용한다. provider SDK가 필요하면 adapter 한 파일에만 가두고 선택 설치로 둔다.
- **프롬프트 문구는 사용자 승인 전까지 작성하지 않는다.** 이 가이드는 프롬프트에 들어갈 자리(slot)와 버전 관리 방식만 정한다.
- 예시 대화, 합성 평가 데이터를 만들지 않는다. 단위 테스트는 더미 레이블 표(정답·예측 ID만 있는 표)로 한다.
- 모델 출력, API 키, 실행 로그는 Git에 넣지 않는다. `results/`는 `.gitignore`로 제외되어 있다.
- 모델 결과를 본 뒤 gold, 후보 풀, split, 지표 정의를 바꾸지 않는다. 바꿔야 하면 버전을 올리고 이유를 기록한다.
- 검사하지 않은 항목을 통과했다고 쓰지 않는다. 수치는 실제 실행 결과만 적는다.

## 1. 평가 조건과 입력 정리

### 1.1 조건

| 실험 | 조건 | 입력 | 답 형식 |
|---|---|---|---|
| N (자연) | `full_mcq` | full_text + target_marker + candidates | entity ID |
| N | `local_mcq` | local_text + target_marker + candidates | entity ID |
| N | `full_qa_subset` (held-out 약 24개) | full_text + target_marker, candidates 없음 | 자유 서술 → entity ID로 정규화 |
| A (정답 전환) | `pair_v1`, `pair_v2` | 각 버전의 full_text + 동일 target_marker + 동일 candidates | entity ID |
| B (정답 불변 최근성) | `early`, `late` | 각 버전의 full_text + 동일 target_marker + 동일 candidates | entity ID |

### 1.2 입력 파일

- 자연 자료: `data/processed/items_v1.jsonl` (자료 담당이 생성). 필드: item_id, target_id, conversation_id, split, full_text, local_text, target_marker, target_speaker_label, candidates, gold_entity_id, full_token_estimate.
- 통제 자료: `data/processed/controlled_v1.jsonl`. 필드: item_id, family_id, pair_id, experiment(A|B), version(v1|v2 또는 early|late), full_text, target_marker, target_speaker_label, candidates, gold_entity_id, designated_distractor_id(B만), compound_order(B만, bool).
- 두 파일 모두 **gold 열은 평가 코드만 읽는다.** 요청 생성 함수의 시그니처에 gold를 넣지 않는다.

### 1.3 후보(candidates) 규칙

- 대화 참여자 `A`, `B`와 포함 범위의 제3자 전부. 정답 기준으로 편리한 비정답만 고르지 않는다.
- 후보 라벨은 지칭 연결에 필요한 최소 정보만 담는다. role이나 의미 힌트를 넣지 않는다.
- pair 안에서는 후보 집합과 순서를 고정한다. pair 사이 순서는 seed로 균형화한다.
- 후보 수는 항목마다 다를 수 있다. 결과표에 후보 수별 결과와 무작위 기대치(1/후보 수의 평균)를 함께 낸다.

## 2. 모델 선정과 설정 고정

### 2.1 선정 기준

MVP는 성격이 다른 2개다. 아래 표를 채워 팀에서 결정하고 `configs/study.json`의 `models[].model_id`에 넣는다. 결정 전까지 null을 유지한다.

| 기준 | 확인 방법 | 기록 위치 |
|---|---|---|
| 성격 차이 | 제조사·규모·reasoning 설정 중 하나 이상이 다름 | `docs/model_selection.md` |
| 구조화 출력 지원 | JSON 강제 또는 동등 기능 유무 | 같은 문서 |
| seed 지원 | 지원 여부와 재현성 수준 | 같은 문서 |
| 입력 한도 | Full prefix 최대 길이를 토크나이저로 센 값이 한도 안인지 | 같은 문서 |
| 비용 | 2.3의 호출 수 × 토큰 추정 | 같은 문서 |
| 접근 환경 | API 키 발급 주체, 데이터 외부 전송 허용 여부(말뭉치 약정 확인) | 같은 문서 |

논문에 등장한 모델을 현재 사용 가능 모델로 자동 대체하지 않는다.

### 2.2 고정해야 하는 설정

실행마다 `config.json`에 아래를 전부 기록한다.

- 정확한 model ID 또는 checkpoint
- 실행 날짜, API/provider, endpoint 버전
- prompt 버전(파일 해시 포함)과 입력 포맷 버전
- decoding 설정(temperature 등), output token budget, reasoning 설정
- seed 값과 지원 여부
- 구조화 출력 강제 여부(모든 조건에서 동일해야 함)
- 재시도 규칙과 timeout

### 2.3 호출 수와 길이 참고치

본 실험 기준 호출 수(설계안 13.1): 80×2조건×2모델 + 48×2모델 + 24×2모델 = 464회. 개발 실험, 재시도, 정규화 재검토를 더해 예산은 약 2배로 잡는다.

2025 구어 2인 대화 63개의 길이(화자 라벨 포함 글자 수, 2026-10-10 점검):

| 항목 | 글자 수 |
|---|---|
| 대화 전체 중앙값 | 6,462 |
| 대화 전체 최대 | 8,959 |
| Full prefix 중앙값 | 3,254 |
| Full prefix 95분위 | 6,575 |

토큰 수는 모델별 토크나이저로 다시 센다. 한도를 넘는 항목은 제외하고 길이와 비율을 보고한다(설계안 3.3). 임의의 짧은 창으로 바꾸지 않는다.

## 3. 프롬프트 자리와 버전 관리 (`prompts/`)

문구는 승인 후 작성한다. 지금은 구조만 정한다.

- 파일: `prompts/mcq_v{n}.json`, `prompts/qa_v{n}.json`. 각 파일은 `{version, created, slots, template}` 구조다. `template`은 승인 전까지 빈 문자열이다.
- slot 목록(고정): `{dialogue}`, `{target_utterance}`, `{target_marker}`, `{target_speaker_label}`, `{candidates}`, `{output_schema}`. Local 조건은 `{dialogue}`에 local_text가 들어간다.
- 주 prompt는 1개다. second prompt와 repeated decoding은 robustness 확장으로 두고 기본 범위에 넣지 않는다.
- 개발 자료에서 demonstration을 쓰기로 하면, held-out과 같은 source·family가 아닌지 확인하는 검사를 코드에 넣는다.

## 4. 실행기 (`src/koimplicit/runner.py`)

### 4.1 adapter 인터페이스

```python
class ProviderAdapter(Protocol):
    def complete(self, request: dict) -> dict:
        """request = {model_id, system, user, decoding, output_schema, seed}
        return  = {raw_text, input_tokens, output_tokens, latency_ms, finish_reason, error}"""
```

- provider별 구현은 `src/koimplicit/providers/{name}.py` 한 파일씩. 표준 라이브러리 `urllib`로 호출 가능하면 SDK를 쓰지 않는다.
- 키는 환경 변수에서만 읽고 로그에 출력하지 않는다.

### 4.2 요청 생성

```python
def build_request(item: dict, condition: str, prompt: dict, run_config: dict) -> dict
def payload_hash(request: dict) -> str   # model_id + prompt 버전 + 채워진 본문의 sha256
```

- 항목마다 독립 요청. 대화 history를 쌓지 않는다. pair의 다른 버전이나 이전 답이 같은 요청에 들어가면 안 된다.
- `build_request`는 gold를 받지 않는다. 테스트에서 시그니처를 고정한다.

### 4.3 실행과 캐시

- `results/runs/{run_id}/cache/{payload_hash}.json`에 응답을 저장한다. 같은 해시는 다시 보내지 않는다.
- 재시도는 네트워크·서버 오류(timeout, 5xx, 연결 실패)만, 같은 payload로 최대 2회. 정답 오류나 형식 오류를 보고 다른 힌트로 재질문하지 않는다.
- 2회 재시도 후에도 실패하면 `status = missing`으로 기록하고 다음 항목으로 넘어간다.
- 실행 순서는 seed로 섞되 `requests.jsonl`에 순서를 남긴다.

### 4.4 기록 파일 (`results/runs/{run_id}/`)

| 파일 | 한 줄의 내용 |
|---|---|
| `config.json` | 2.2의 설정 전부, items 파일 해시, prompt 파일 해시, split manifest 해시 |
| `requests.jsonl` | item_id, condition, model_label, payload_hash, order |
| `responses.jsonl` | item_id, condition, model_label, payload_hash, raw_text, input_tokens, output_tokens, latency_ms, finish_reason, retries, status(ok/missing/invalid) |
| `normalized.jsonl` | 5절의 출력 |

run_id는 `{YYYYMMDD}_{model_label}_{experiment}_{prompt_version}` 형식으로 한다.

### 4.5 CLI

`python -m koimplicit run --items data/processed/items_v1.jsonl --split development --conditions full_mcq,local_mcq --model model_a --prompt prompts/mcq_v1.json --seed 20261010`

held-out 실행은 분석 계획이 동결된 뒤 한 번만 한다(7절).

## 5. 출력 정규화 (`src/koimplicit/normalize.py`)

### 5.1 MCQ

- 구조화 출력이면 지정 필드에서 entity ID를 읽는다. 후보 집합에 없는 ID, 여러 ID, 빈 값은 `invalid`.
- 비구조화 출력이면 후보 ID와 정확히 일치하는 토큰 하나를 찾는다. 0개 또는 2개 이상이면 `invalid`.
- 모델이 명시적으로 답을 거부하면 `abstain`. 오답으로 세되 invalid와 따로 집계한다.
- 결과 필드: item_id, condition, model_label, predicted_entity_id, parse_status(ok/invalid/abstain/missing).

### 5.2 QA

QA 응답은 후보 목록 없이 나온 서술이므로 entity ID로 매핑한다.

1. 규칙 단계: 응답에서 이름(name 플레이스홀더), 지칭 표현, 현재 발화 기준 대명사(나/너 등)를 찾아 목표 발화의 화자·청자 또는 roster의 제3자로 매핑한다. 매핑 표는 `items_v1.jsonl`의 candidates와 target_speaker_label에서 만든다.
2. 여러 인물을 함께 답하거나 근거 없이 매핑할 수 없으면 `unmapped`로 두고 실패로 처리한다.
3. 규칙으로 처리하지 못한 출력은 `results/runs/{run_id}/qa_review_queue.jsonl`로 내보낸다. 검토자에게는 응답 텍스트와 roster만 보여 주고 **모델 이름과 gold를 가린다.** 검토 결과는 `qa_review_done.jsonl`에 검토자 ID와 함께 저장한다.
4. 규칙 매핑률, 인간 검토율, 최종 실패율을 보고한다.

MCQ와 QA의 차이는 형식의 영향으로 보고한다. 후보 수, 제공 정보, 판정 기준이 다르므로 차이를 전부 언어 능력으로 설명하지 않는다.

## 6. 지표 (`src/koimplicit/metrics.py`)

### 6.1 정의

각 항목의 정답 여부를 c ∈ {0, 1}로, pair의 두 버전을 c1, c2로 둔다. invalid·abstain·missing은 모두 c = 0이지만 별도 열로 센다.

| 함수 | 정의 | 분모 |
|---|---|---|
| `entity_accuracy` | 정답 entity 출력 수 / 평가 대상 수 | 조건·모델별 전체 항목 |
| `role_accuracy` | 예측 entity를 목표 발화 기준 role로 바꾼 뒤 정답 role과 일치한 수 / 대상 수 | 같음 |
| `same_role_wrong_entity_rate` | role은 맞고 entity는 틀린 수 / 대상 수 | 같음 |
| `pair_accuracy` | Σ(c1 × c2) / 전체 쌍 수 | 유효 pair |
| `paired_harm` | c1 = 1, c2 = 0인 쌍 / 전체 쌍 수 | B는 early→late, A는 v1→v2 |
| `paired_recovery` | c1 = 0, c2 = 1인 쌍 / 전체 쌍 수 | 같음 |
| `distractor_rate` | designated distractor 출력 수 / 해당 조건 대상 수 | B의 각 조건 |
| `full_local_paired_diff` | 같은 항목의 Full 정답 − Local 정답의 평균 | 두 조건 모두 응답이 있는 항목 |

주지표는 세 개다: Natural Full entity accuracy, A pair accuracy, B paired harm. 가중 합산 단일 점수는 만들지 않는다.

### 6.2 보조표

- role별(speaker / addressee / third_party) accuracy. 전체는 micro, role macro는 보조.
- 문맥 필요성별(locally recoverable / discourse-dependent) Full·Local 결과.
- entity 변화 × speaker 변화 셀별 결과와 실제 표본 수, shift NA 비율.
- 후보 수별 결과와 무작위 기대치.
- 거리 구간별(last_mention_distance, support_distance) 결과. 단위는 `speaker_run_proxy`로 표기.
- invalid / abstain / missing 비율을 조건·모델별로.
- B에서 compound_order = true인 쌍은 주 최근성 분석에서 제외하고 따로 보고.

### 6.3 데이터 형식

입력은 `normalized.jsonl`과 gold가 있는 items 파일을 item_id로 join한 표다. 지표 함수는 이 join 결과(list[dict])를 받고 `{value, numerator, denominator}`를 반환한다. 분모를 항상 같이 반환해야 CI 계산과 보고가 맞는다.

## 7. 통계 (`src/koimplicit/bootstrap.py`)

### 7.1 cluster bootstrap

```python
def cluster_bootstrap(rows, cluster_key, statistic, n_boot=2000, seed=...) -> {point, ci_low, ci_high, n_rows, n_clusters}
```

- 자연 자료: `cluster_key = conversation_id`.
- 통제 자료: `cluster_key = family_id`. pair는 family 안에 묶여 있으므로 쌍이 보존된다.
- 재표집은 cluster를 복원 추출하고 그 안의 행을 전부 가져온다. 행 단위로 섞지 않는다.
- 조건 차이(Full − Local)와 모델 차이도 **같은 재표집**에서 계산한다. 두 조건을 따로 bootstrap해서 빼지 않는다.
- 95% percentile CI, 원래 행 수, 독립 cluster 수를 함께 반환한다.

### 7.2 보고 규칙

- 출력 수가 독립 표본 수를 대신하지 않도록 모든 표에 cluster 수를 적는다.
- 통제 실험은 12쌍/실험이라 pilot에 가깝다. CI와 함께 개별 쌍 결과와 원시 변화 개수(정답→오답, 오답→정답)를 그대로 싣는다.
- 유의/비유의로 강하게 결론 내리지 않는다.
- mixed-effects logistic regression은 논문 확장 단계로 미룬다. MVP 코드에 넣지 않는다.

## 8. 기준선 (`src/koimplicit/baselines.py`)

| 기준선 | 구현 | 보고할 것 |
|---|---|---|
| Majority entity-role prior | 개발 자료의 role 분포에서 최빈 role을 고르고, third_party면 사전 지정 규칙(예: 가장 최근 언급된 제3자)으로 entity 선택 | 규칙 문서화, held-out 적용 결과 |
| Most-recent explicit NP | prefix에서 마지막으로 나온 고유 이름/명시 지칭을 선택. 후보 roster에 매핑되지 않으면 실패 | 매핑 실패율 |
| Most-recent entity (oracle) | 인간 mention-to-entity 매핑을 써서 마지막 언급 entity 선택 | gold 도움을 받는 진단 기준선임을 명시 |
| 동일 LLM Local 입력 | 4절의 `local_mcq` 실행 결과 | 앞선 문맥의 추가 효과 |
| 규칙 기반 cue baseline (선택) | 종결어미·경어 규칙으로 speaker/addressee 추정 | 규칙과 적용 범위 공개, 선행 연구 재현으로 과장하지 않음 |

기준선 비교보다 인간 정보 충분성 판정이 먼저다. 기준선은 Full unique 항목에만 적용한다.

## 9. 분석 계획 동결과 실행 순서

1. 개발 자료(약 40개)에서 두 모델을 `full_mcq`, `local_mcq`로 실행한다.
2. 파싱 규칙, QA 정규화 규칙, 오류 유형 목록, 보조표 구성을 확정한다.
3. `docs/analysis_plan_v1.md`에 다음을 적고 동결한다: 주지표 3개, 보조표 목록, cluster 정의, 제외 규칙(입력 한도 초과, invalid 처리), 후보 수별 기대치 계산법, 동결 날짜와 관련 파일 해시.
4. held-out 80개와 통제 48개를 **한 번** 실행한다. QA subset 24개는 모델 결과를 보기 전에 선택한 목록을 쓴다.
5. 조건 사이 missing이 불균형하면 공통 성공 집합 결과와 실패를 불리하게 계산한 민감도 분석을 함께 낸다.
6. 결과표와 그림을 `results/analysis/`, `results/figures/`에 저장하고 생성 명령을 `results/analysis/run_log.md`에 남긴다.

동결 후 바뀐 것은 `analysis_plan_v2.md`로 남기고 v1과의 차이를 적는다.

## 10. 해석 규칙 (결과 작성 시 그대로 적용)

| 관찰 | 허용되는 해석 |
|---|---|
| Full > Local | 제공된 앞선 문맥이 이 조건에서 도움이 됨 |
| Full < Local | 허용되는 결과. 불필요한 인물 언급이 늘었는지 함께 분석 |
| A 양쪽 정답 | 정답을 바꾸는 관련 문맥을 올바르게 활용. 답만 바꾼 것은 성공이 아님 |
| B late에서 distractor 증가 | 검증된 해당 개입에서 최근 언급에 민감한 행동 |
| B 양쪽 같은 오답 | robustness 성공으로 세지 않음 |
| Local 강제 선택 정확도 낮음 | 정보 제거 진단치. 인간도 못 푸는 항목의 낮은 정확도를 모델 결함으로 세지 않음 |
| 어미 제거 후 하락 | 제거된 단서의 영향. shallow reasoning 증거로 자동 해석하지 않음 |
| shift 셀 간 차이 | 해당 표본에서의 연관. 독립 인과 효과 아님 |
| 모델 설명이 담화 추적을 언급 | 생성된 설명. 처리 메커니즘의 검증 아님 |

## 11. 테스트 (`tests/`)

- `test_metrics.py`: 더미 레이블 표로 6.1 함수 전부. 분모 0, invalid·abstain·missing 처리, pair 한쪽 missing 처리를 포함한다.
- `test_bootstrap.py`: cluster 1개일 때 CI가 point와 같음, 같은 seed로 같은 결과, 조건 차이가 같은 재표집에서 계산됨을 확인.
- `test_normalize.py`: 후보 밖 ID, 복수 ID, 빈 응답, 거부 응답의 parse_status. QA 규칙 매핑은 roster와 라벨만 있는 더미 표로.
- `test_runner.py`: `build_request`가 gold 필드를 받지 않음, 같은 입력의 payload_hash가 같음, 재시도가 네트워크 오류에만 적용됨(가짜 adapter 사용).
- 실제 API를 호출하는 테스트는 두지 않는다.

## 13. 하지 말 것

- gold를 요청 생성 함수에 넘기는 것.
- 형식 오류나 오답을 보고 같은 항목을 다른 힌트로 다시 묻는 것.
- 조건마다 구조화 출력 강제 여부를 다르게 하는 것.
- pair의 두 버전을 한 요청이나 한 대화 history에 넣는 것.
- 모델이 틀린 항목만 골라 gold를 재검토하는 것.
- 세 주지표를 가중 합산한 leaderboard 점수를 만드는 것.
- held-out 결과를 보고 prompt, 파싱 규칙, 제외 기준을 바꾸는 것.
- 모델 출력, 원문, API 키를 커밋하는 것.
