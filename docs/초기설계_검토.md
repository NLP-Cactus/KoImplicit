## 1. 예시 문제의 정답이 흔들린다

**요약:** 우리가 정한 정답 말고 다른 답도 말이 되면 안 된다.

시험 문제를 냈는데 학생이 "2번도 답이 되는데요?"라고 하면 그 문제는 폐기해야 한다. 설계안의 예시가 그런 상태다.

> 민수가 프로젝트를 맡았다.
> 지훈이는 자료 조사를 도왔다.
> ( ) 발표**도** 준비했다.

정한 정답은 민수다. 문제는 '**도**'다. "철수는 청소를 했다. 숙제**도** 했다"에서 숙제한 사람은 철수다. '도'는 바로 앞 사람이 한 일에 하나를 더하는 말이라서, 위 문장은 "**지훈이가** 조사도 하고 발표도 했다"로 읽힌다.

그러면 다음과 같은 문제가 생긴다.
- 모델이 지훈이를 고르면 실제로는 제대로 읽은 것인데, 우리는 "최근 이름을 골랐다"고 잘못 결론 내린다.
- 연구의 핵심 증거(recent-entity bias)가 오염된다.

§6 Shift 예시도 같은 문제다. "지훈이는 집에 있었대. → 근데 ( ) 과제는 냈대?"는 문서에 "추가 단서가 반드시 있어야 한다"고 써 놓고도 정작 그 단서가 없다.

**고치는 법:** 정답이 하나로 확정되도록 이유를 넣는다.

> 민수가 프로젝트를 맡았다. 지훈이는 자료 조사를 도왔다.
> 민수는 팀장이니까 ( ) 발표를 맡았다.

문제를 만들지 않은 사람이 읽어도 같은 답이 나오는지 반드시 확인한다. spec 문서의 대표 예시가 틀리면 generator가 그 오류를 수백 개로 복제한다.

## 2. 화자 표시를 지우면 선택지가 무너진다

**요약:** "화자 A"라는 선택지는 A라는 표시가 있어야만 의미가 있다.

현재 문제 형식:
```
A: 너 내일 와?
B: 응, ( ) 갈게.

선택지: A. 화자 A   B. 화자 B   C. 민수
```

Phase 2에서 화자 표시가 없으면 모델이 헷갈리는지 보려고 A:, B:를 지우면:
```
너 내일 와?
응, ( ) 갈게.

선택지: A. 화자 A   B. 화자 B   ← 화자 A가 누구인지 정의되지 않음
```

대화에 A가 없는데 선택지에 "화자 A"가 남아서 문제가 성립하지 않는다. 또 선택지 기호 "A."와 화자 이름 "A"가 같은 글자라서, "A를 골랐다"가 선택지 A인지 화자 A인지 애매하다.

**고치는 법:**
- 화자에게 이름을 붙인다 (예: 서연, 지호).
- 표시를 지운 버전에서는 선택지를 "먼저 말한 사람 / 나중에 말한 사람"으로 바꾼다.
- 선택지 기호는 숫자(1, 2, 3, 4)로 바꾼다.

## 3. "판단할 수 없음" 선택지가 결과를 흐린다

**요약:** 틀린 이유 두 가지가 섞여서 구분할 수 없다.

Correct-Detect 논문의 "판단 보류를 남발하는 학생"과 같은 문제다. 선택지에 "E. 판단할 수 없음"이 있으면 모델이 틀리는 이유가 둘이 된다.

1. 대화를 따라가지 못해 엉뚱한 사람을 골랐다 ← **우리가 알고 싶은 것**
2. 판단을 보류해 "판단할 수 없음"을 골랐다 ← 우리 연구 질문과 무관

정답률이 70%로 나와도 어느 쪽 때문인지 알 수 없다. 게다가 논문에서 보았듯이 판단 보류 성향은 프롬프트 한 줄로도 크게 바뀐다 (GPT-4o 탐지율 22.86% → 99.55%).

**고치는 법:** 메인 실험에서는 "판단할 수 없음"을 빼고 반드시 한 명을 고르게 한다. 판단 보류는 정말 모호한 문항만 모은 별도 세트(AMBIGUOUS)에서만 측정한다.

## 4. 선택지 개수가 다르면 비교가 불공평하다

**요약:** 4지선다와 5지선다 점수를 비교하면 안 된다.

| 조건 | 선택지 | 무작위로 골랐을 때 정답 확률 |
|---|---|---|
| Distractor 없음 | 화자A, 화자B, 민수, 모름 (4개) | 25% |
| Distractor 있음 | 화자A, 화자B, 민수, 지훈, 모름 (5개) | 20% |

distractor 조건에서 점수가 떨어졌을 때, 지훈이에게 속아서인지 보기가 하나 늘어서인지 구분할 수 없다.

**고치는 법:** minimal pair끼리는 선택지 집합을 똑같이 맞춘다. distractor 없는 버전에도 지훈이를 대화 앞쪽에 한 번 등장시킨다. 그러면 두 버전의 차이는 "지훈이가 **바로 앞에** 나왔는가" 하나만 남는다.

## 5. Pilot 72문항으로는 판단하기에 너무 적다

**요약:** 문항이 적으면 우연에 의한 점수 변동이 크다.

동전을 10번 던져 앞면이 7번 나와도 "앞면이 잘 나오는 동전"이라고 할 수 없다. 횟수가 적으면 우연의 영향이 크다.

Pilot에서 Shift 조건은 모델당 36문항이다. 정답률이 80%라면 95% 신뢰구간이 약 **±13%p**라서, "Control 91% / Shift 78%" 정도의 차이는 우연 범위 안에 들어간다. 칸(cell)당 6문항이므로 칸별 해석은 불가능하다.

**고치는 법:** GO 기준을 점수 차이 대신 방향성으로 바꾼다.
- 모델 3개가 **모두 같은 방향**으로 성능이 떨어지는가
- 오답 중 **distractor를 고른 비율**이 무작위 선택 수준보다 뚜렷하게 높은가

또는 Pilot을 144문항으로 늘린다.

Distance를 "1/3 일부 포함"으로 하면 다른 조건과 교차가 맞지 않아 효과가 섞인다. Pilot에서는 distance=1로 고정한다.

## 6. 아직 정의되지 않은 것들

**요약:** 규칙이 애매하면 팀원마다 다른 기준으로 문항을 만든다.

### (1) Addressee(청자) 예시가 없다
세 범주 중 하나인데 설명이 "조건에 따라…"로 끝난다. 예를 들면 다음과 같은 예시를 확정해야 한다.

> 서연: ( ) 점심 먹었어? → 듣는 사람(지호)이 먹었는지 묻는 것

### (2) Speaker(화자)일 때 Shift의 의미가 없다
Shift는 "직전에 이야기하던 사람에서 다른 사람으로 바뀜"이다. 정답이 말하는 사람 자신일 때 "직전에 이야기하던 사람"이 누구인지 기준이 없다.

→ 12칸 표(3 referent × 2 shift × 2 distractor)를 만들고 칸마다 예시를 하나씩 직접 써 본다. 예시를 쓸 수 없는 칸이 정의가 비어 있는 곳이다.

### (3) Ambiguous 예시가 실제로는 모호하지 않다
> 민수랑 지훈이 만났어? → 응. ( ) 밥도 먹었대.

"민수인지 지훈인지 모른다"가 아니라 "**둘이 함께** 먹었다"로 읽는 것이 자연스럽다. 분류표에 "둘 다" 범주가 없다. `BOTH/GROUP`을 추가하거나 예시를 바꾼다.

관련 연구: *Can LLMs Detect Ambiguous Plural Reference? An Analysis of Split-Antecedent and Mereological Reference* (arXiv:2510.04581). 관련 연구 담당이 확인 필요.

### (4) 정답 표기 방식이 문서마다 다르다
§3 schema는 정답을 `"민수"`(이름)로, §12 결과 schema는 `entity_01`(ID)로 적는다. 구현 시 반드시 꼬인다.

→ 문항마다 등장인물 목록(`entities`: id, 이름, 역할)을 두고 gold는 ID로 통일한다. 변형 종류를 기록하는 `variant_type`(original / label_removed / distractor_added …) 필드도 미리 넣는다.
