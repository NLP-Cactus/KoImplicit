# 말뭉치 활용 구현 가이드

- 작성일: 2026-10-10
- 대상: 자료 담당 팀원 (설계안 13.3의 source parser·speaker/turn 확인·분할 역할)
- 기준 문서: [최종설계안.md](../최종설계안.md) v2.0, [AGENTS.md](../AGENTS.md)
- 상태: `data/raw/`의 2025 구어 파일을 자동 전수 점검한 결과를 바탕으로 쓴 구현 지침이다. 설계안 4.2의 정식 audit(사람이 30~50개 확인)은 아직 하지 않았다.

## 0. 전제와 규칙

- `data/raw/` 원본은 읽기만 한다. 변환 결과는 `data/interim/`, `data/processed/`, `data/manifests/`에 쓴다. 이 폴더들은 `.gitignore`로 제외되어 있으므로 강제 추가하지 않는다.
- Python 3.10 이상, 표준 라이브러리만 사용한다. 새 패키지와 framework를 넣지 않는다.
- 말뭉치의 복원형 문자열(`내가`, `화자가`, `name1이` 등)은 정답을 노출한다. **모델 입력과 인간 판정자 화면에 절대 들어가면 안 된다.** 파서 단계부터 별도 파일로 격리한다.
- 문항, 예시 대화, 평가 프롬프트는 만들지 않는다. 이 가이드의 범위는 파서, 필터, audit 지원, split, payload 생성 코드까지다.
- 코드·문서에 실제 문장 원문과 문서 ID를 넣지 않는다. 테스트 fixture도 마찬가지다.
- 커밋 메시지는 Conventional Commits(`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`)로 쓰고 AI 서명을 붙이지 않는다.

## 1. 입력 자료 사실 요약

### 1.1 파일 구성

| 폴더 | 파일 | MVP 용도 |
|---|---|---|
| `data/raw/말뭉치2025.0/` | 구어 ZA JSON(`SXZA25…`), 신문 ZA JSON(`NXZA25…`), 설명서 PDF(국문·영문) | **구어 JSON이 주자료.** 신문은 사용하지 않음 |
| `data/raw/말뭉치2024/` | 구어 ZA JSON(`SXZA24…`), 신문 ZA JSON(`NXZA24…`), 설명서 PDF | MVP 제외. 화자 정보가 없어 원본(일상 대화 2022) join 전에는 쓸 수 없음 |

2025 구어의 원본은 **일상 대화 말뭉치 2024**다(설명서 명시). 2024 ZA의 원본은 일상 대화 2022라서 두 판을 합치지 않는다.

### 1.2 2025 구어 JSON 구조

```text
{id, metadata, document[]}
document[]:
  id                      # 대화 하나 = 문서 하나
  metadata
    title                 # "2인 일상 대화" | "1인 사적 독백" | "1인 공적 독백"
    topic, date
    speaker[]             # {id, age, sex, occupation, ...}
    setting               # {relation, contact_frequency}
  sentence[]
    id                    # 점(.)으로 구분된 계층 ID. 4단과 5단이 섞여 있음
    form                  # 정제문. 모든 offset의 기준
    original_form         # 원 전사문. 약 22% 문장에서 form과 다름(주로 "어/음" 제거, 띄어쓰기)
    speaker_id            # metadata.speaker[].id와 1:1 연결됨
    word[]                # {id, form, begin, end}
    ZA[]
      predicate           # {form, sentence_id, word_id, begin, end}
      ellipsis[]
        restored          # {form, type}  type ∈ subject | object | adjunct | complement
        antecedent[]      # {form, sentence_id, begin, end}
```

### 1.3 반드시 처리해야 하는 규약

| 항목 | 사실 | 처리 |
|---|---|---|
| 선행사 없음 | `antecedent.form == "#"` 이면 텍스트 선행사가 없는 지시적 사례. `sentence_id`도 `"#"`이거나, 값이 있어도 대부분 **문서 첫 문장을 가리키는 placeholder** | form이 `#`이면 sentence_id·begin·end를 무시하고 `has_textual_antecedent=false`로 기록 |
| 후행 선행사 | 주어 복원의 약 1.6%가 목표 문장보다 **뒤** 문장을 선행사로 둠 | 문장 순서로 판정해 `has_future_antecedent=true` 플래그. 필터에서 제외 |
| 복수 선행사 | 한 ellipsis에 antecedent가 2개 이상인 경우 있음 | 리스트 그대로 보존. 관계(same/earlier/later)는 각각 계산 |
| 빈 antecedent | 드물게 `antecedent: []` | `has_textual_antecedent=false`, `antecedent_missing=true` |
| ID 깊이 | 문장 ID가 4단과 5단으로 섞여 있음 | 깊이를 가정하지 말고 **배열 순서**를 순서의 기준으로 사용. ID는 키로만 사용 |
| turn 없음 | turn 필드가 없음. 동일 화자 연속 문장이 평균 6.5개, 최대 39개 | speaker-run 번호를 계산해 붙이고 `distance_unit = speaker_run_proxy`로 기록 |
| 복원형이 역할 노출 | 텍스트 선행사가 없으면 `화자가/청자가`, 있으면 `내가/네가`류로 복원됨 | 격리 파일에만 저장. reference_mode 1차 힌트로만 사용 |
| 이름 익명화 | 인명은 `name1`, `name2`… 로 치환됨. 제3자는 주로 관계 명사(엄마, 선생님 등) | 후보 roster에 그대로 사용. 인물 통합은 인간 주석에 맡김 |

### 1.4 전수 점검으로 확인된 수치 (파서 회귀 검사용)

파서가 아래 수치를 재현해야 한다. 하나라도 다르면 파서 버그다.

| 항목 | 값 |
|---|---|
| 문서 수 | 75 (2인 일상 대화 63, 1인 독백 12) |
| 문장 수 | 16,439 |
| ZA predicate 수 | 18,535 |
| ellipsis 수 | 24,871 (subject 16,838 / object 4,429 / adjunct 3,564 / complement 37 / type 없음 3) |
| speaker_id가 화자 목록에 없는 문장 | 0 |
| 문장 ID 순서가 배열 순서와 다른 문서 | 0 |
| predicate offset이 form과 불일치 | 0 |
| antecedent offset이 form과 불일치 (`#` 제외) | 0 |
| form ≠ original_form 문장 | 3,597 |

## 2. 1단계 파서 (`src/koimplicit/corpus.py`)

### 2.1 목표

원본 JSON을 대화 단위의 평탄한 JSONL 세 개로 바꾼다. 이후 모든 단계는 원본이 아니라 이 파일들만 읽는다.

### 2.2 출력 파일 (`data/interim/`)

**`utterances.jsonl`** 문장당 한 줄

| 필드 | 타입 | 설명 |
|---|---|---|
| conversation_id | str | document.id |
| conversation_type | str | metadata.title 값 |
| order | int | 문서 내 배열 순서, 0부터 |
| sentence_id | str | 원본 ID |
| speaker_id | str | 원본 speaker_id |
| speaker_label | str | 대화 내 첫 등장 순으로 `A`, `B`. 모델 입력용 중립 라벨 |
| run_index | int | speaker-run 번호. 화자가 바뀔 때마다 +1 |
| form | str | 정제문 |
| original_form | str | 원 전사문 |
| form_differs | bool | form ≠ original_form |

**`targets.jsonl`** subject ellipsis당 한 줄 (object·adjunct는 별도 집계만 하고 쓰지 않음)

| 필드 | 타입 | 설명 |
|---|---|---|
| target_id | str | `{conversation_id}:{sentence_id}:{predicate_word_id}:{ellipsis_index}` |
| conversation_id, sentence_id, order | | utterances와 join 키 |
| speaker_id, speaker_label | | 목표 발화의 화자 |
| predicate_form, predicate_word_id, predicate_begin, predicate_end | | 원본 그대로 |
| restored_type | str | 항상 `subject` |
| antecedents | list | `[{form, sentence_id, begin, end, relation}]`. relation ∈ `same` / `earlier` / `later` / `none` / `missing_sentence` |
| has_textual_antecedent | bool | form이 `#`이 아닌 antecedent가 하나 이상 |
| has_future_antecedent | bool | relation이 `later`인 antecedent가 하나 이상 |
| antecedent_missing | bool | antecedent 배열이 비어 있음 |
| last_textual_antecedent_distance | int or null | 가장 가까운 earlier/same 선행사까지 문장 수 차이. 없으면 null |

**`gold_hints.jsonl`** 격리 파일. target_id당 한 줄

| 필드 | 설명 |
|---|---|
| target_id | |
| restored_form | 원본 복원형 문자열 |
| hint_category | `speaker_pronoun` / `speaker_deictic`(화자가) / `addressee_pronoun` / `addressee_deictic`(청자가) / `name_placeholder` / `generic_or_plural` / `other` |

이 파일은 필터 단계의 입력이고, 그 이후 단계(audit 시트·payload)에서는 읽지 않는다. 코드에서 import 경로로 분리해 두면 실수를 막기 쉽다.

### 2.3 함수 설계

```python
def load_spoken_release(path: Path) -> dict            # json.load 한 번. 파일이 40MB라 전체 로드로 충분
def iter_conversations(release: dict) -> Iterator[dict] # document[]를 순회
def flatten_utterances(doc: dict) -> list[dict]        # speaker_label, run_index 계산
def flatten_targets(doc: dict, order_index: dict) -> tuple[list[dict], list[dict]]  # targets, gold_hints
def write_jsonl(rows, path)                            # ensure_ascii=False
def parse_release(raw_path, interim_dir) -> dict       # 위를 묶고 1.4 수치의 집계 dict를 반환
```

- `relation` 계산은 `order_index[sentence_id]`와 목표 문장 order의 비교로 한다. antecedent의 sentence_id가 문서에 없으면 `missing_sentence`.
- `speaker_label`은 대화마다 새로 매긴다. 독백 문서는 `A` 하나다.
- `hint_category` 판정 어휘 목록은 모듈 상수로 두고 테스트에서 고정한다. 초기 목록은 아래 3.2를 참고.

### 2.4 CLI

`python -m koimplicit parse --raw "data/raw/말뭉치2025.0/<2025 구어 ZA JSON>" --out data/interim`

실행 후 1.4의 집계를 `data/interim/parse_report.json`으로 저장하고 화면에도 출력한다. 기존 `status` 명령은 그대로 둔다.

### 2.5 테스트 (`tests/test_corpus.py`)

- 실제 raw 파일이 있을 때만 실행되는 회귀 테스트: 1.4의 수치를 assert. 파일이 없으면 `unittest.skip`.
- 규약 단위 테스트: `#` antecedent, 후행 antecedent, 5단 ID, 빈 antecedent를 각각 포함한 **최소 구조 fixture**로 relation·플래그 계산을 확인한다. fixture 문장은 `"문장1"`, `"문장2"` 같은 placeholder만 쓰고 실제 대화를 흉내 내지 않는다.
- offset 테스트: 모든 predicate와 `#`이 아닌 antecedent에 대해 `form[begin:end] == 해당 form`을 전수 확인.

## 3. 2단계 후보 필터 (`src/koimplicit/candidates.py`)

### 3.1 목표

설계안 3.1 포함 범위를 자동 규칙으로 1차 적용하고, 제외 사유를 전부 기록한다. 여기서 나온 집계가 설계안 3.2가 요구하는 제외 목록 보고의 근거다.

### 3.2 규칙과 제외 사유 코드

순서대로 적용하고, 처음 걸린 사유 하나만 기록한다.

| 순서 | 사유 코드 | 조건 |
|---|---|---|
| 1 | `NOT_DYAD` | conversation_type이 "2인 일상 대화"가 아님 |
| 2 | `FUTURE_ANTECEDENT` | has_future_antecedent |
| 3 | `ANTECEDENT_MISSING` | antecedent_missing |
| 4 | `GENERIC_OR_PLURAL` | hint_category == generic_or_plural |
| 5 | `NONHUMAN_LEXICON` | restored_form이 비인간 어휘 목록에 포함 (예: 음식, 드라마, 돈, 일, 부분, 생각, 성격). 목록은 모듈 상수로 두고 추가 시 커밋 |
| 6 | `MANUAL_CHECK` | hint_category == other 이고 위에 걸리지 않음. 사람이 단수 인간 여부를 확인해야 함 |
| 없음 | (포함) | speaker/addressee/name_placeholder 범주 |

초기 `generic_or_plural` 어휘: 누군가가, 무언가가, 우리가, 저희가, 사람들이, 사람이, 애들이, 친구들이, 가족이, 부모님이, 그게, 그것이. 이 목록은 복원형 빈도 상위에서 뽑은 것이므로 필터 실행 후 `MANUAL_CHECK` 빈도표를 보고 보강한다.

### 3.3 출력

- `data/interim/candidates.jsonl`: target_id, conversation_id, order, included(bool), exclusion_reason, hint_category, has_textual_antecedent, last_textual_antecedent_distance. **restored_form은 넣지 않는다.**
- `data/interim/candidate_report.md`: 사유별 건수, 포함 건수의 hint_category × has_textual_antecedent 교차표, 대화별 포함 건수 분포(min/median/max), `MANUAL_CHECK` 복원형 빈도 상위 50개.

2026-10-10 점검 기준 참고치: 2인 대화 63개에서 FUTURE 225건, GENERIC 3,154건이 빠지고, 포함 후보가 대화당 중앙값 193개였다. 그중 제3자 name 플레이스홀더는 208건으로 적으므로 role 셀 불균형을 미리 예상해야 한다.

### 3.4 CLI

`python -m koimplicit filter --interim data/interim`

## 4. 3단계 정식 audit 지원 (`src/koimplicit/audit.py`)

### 4.1 목표

사람이 설계안 4.2 표를 채울 수 있게 **서로 다른 대화에서 30~50개** 후보를 뽑고 검토 시트를 만든다. 이 단계는 사람이 한다. 코드는 시트만 만든다.

### 4.2 표집 규칙

- 고정 seed. 대화당 1개, 대화 수가 모자라면 2개까지.
- hint_category를 층으로 써서 speaker / addressee / name_placeholder / MANUAL_CHECK가 모두 들어가게 한다. 층별 수량은 시트에 기록한다.
- 포함 후보뿐 아니라 `MANUAL_CHECK` 항목도 일부 넣어 어휘 목록 보강 근거를 얻는다.

### 4.3 시트 형식 (`data/interim/audit_sheet.jsonl` + 사람이 쓰기 쉬운 `audit_sheet.tsv`)

| 열 | 내용 |
|---|---|
| target_id | |
| context | 대화 시작부터 목표 발화까지, `A: 문장` 형식. 목표 발화의 predicate를 `[[ ]]`로 표시 |
| original_context | 같은 범위의 original_form. form과 다른 문장만 |
| run_boundary_note | 목표 발화가 run의 첫 문장인지 여부 |
| 판정 열(비움) | 대화 연결 OK / 발화자 OK / 순서 OK / 발화 경계 문제 / 서술어 위치 OK / 정답 근거 유형(텍스트·참여자 지시·미래·비지시) / 원문 차이 영향 / 대명사 연결 OK / 메모 |

**복원형과 antecedent 위치는 시트에 넣지 않는다.** 판정자가 원 gold를 모른 채 보게 하는 것이 설계안 5.3의 전제다. 대조는 판정이 끝난 뒤 target_id로 `gold_hints.jsonl`과 join해서 한다.

### 4.4 audit 뒤에 할 일

- 통과하면 `configs/study.json`의 `source.acquired`와 `structure_audited`를 true로 바꾸고 `scope.turn_unit`을 `speaker_run_proxy`로 바꾼다.
- `#` 지시적 항목 대부분이 종결어미·경어만으로 화자/청자가 정해진다고 판정되면 설계안 14의 "대부분 Local로 충분" 분기를 팀에서 논의한다. 코드로 결정하지 않는다.
- 원래 turn 경계가 꼭 필요하다는 결론이 나면 일상 대화 말뭉치 2024 추가 신청을 요청한다.

## 5. 4단계 대화 split과 표집 (`src/koimplicit/split.py`)

### 5.1 split

- 단위는 대화(conversation_id). 2인 일상 대화 63개만 대상.
- 고정 seed로 섞어 약 1/3을 development, 나머지를 heldout으로 한다.
- 출력 `data/manifests/split.json`: `{seed, created, source_file_sha256, development: [...], heldout: [...]}`.
- 한 번 만든 split은 바꾸지 않는다. 바꿔야 하면 새 파일을 버전 번호로 만들고 이유를 적는다.

### 5.2 표집

- 목표 120개(개발 40, held-out 80), 대화당 최대 8개, 20개 이상 대화에 분산.
- 입력은 `candidates.jsonl`에서 included == true인 것. 모델 출력과 무관하게 뽑는다.
- hint_category는 **층화의 참고 정보로만** 쓴다. 정답이나 role로 쓰지 않는다. role 균형을 맞추려고 held-out을 교체하지 않는다.
- 출력 `data/manifests/sample_v1.json`: target_id 목록, split, seed, 층별 수량, 제외된 대화와 이유.

### 5.3 CLI

`python -m koimplicit split --seed 20261010` 그리고 `python -m koimplicit sample --split data/manifests/split.json --seed 20261010`

## 6. 5단계 평가 입력 생성 (`src/koimplicit/payload.py`)

이 단계는 인간 판정(annotations)이 끝나고 gold가 동결된 뒤 실행한다. 지금은 형식과 코드만 준비한다.

### 6.1 입력

- `sample_v1.json`의 target_id
- `annotations/{split}/`의 조정 완료 레코드 (`schemas/annotation.schema.json` 준수). full_resolvability == unique인 것만 payload로 만든다.
- 후보 roster: 대화 참여자 `A`, `B`와 annotation에서 확정된 제3자 entity 목록. 제3자 목록을 사람이 검증했으면 `roster_source = oracle`로 기록한다.

### 6.2 출력 `data/processed/items_v1.jsonl`

| 필드 | 내용 |
|---|---|
| item_id, target_id, conversation_id, split | |
| full_text | 대화 시작부터 목표 발화 끝까지. `A: …` 형식, 정제문(form) 사용 |
| local_text | 목표 발화만, 같은 형식 |
| target_marker | 목표 발화 내 predicate의 begin/end와 문자열 |
| target_speaker_label | |
| candidates | `[{entity_id, label}]`. 정답 여부와 무관한 순서. pair 사이 순서는 seed로 섞고 pair 안에서는 고정 |
| gold_entity_id | 평가 코드만 읽는다. 모델 입력 생성 함수에는 전달하지 않는다 |
| full_token_estimate | 길이 보고용. 모델 한도를 넘는 항목은 제외하고 비율을 보고 |

QA 조건은 같은 full_text에 candidates를 뺀 것이다. 별도 파일로 만들지 않고 생성 함수의 옵션으로 둔다.

### 6.3 주의

- original_form을 쓸지 form을 쓸지는 audit 결과로 정한다. 기본은 form이다. offset이 form 기준이기 때문이다. 바꾸면 manifest에 적는다.
- speaker_label 치환은 utterances.jsonl의 값을 그대로 쓴다. 다시 계산하지 않는다.
- 프롬프트 문자열은 이 모듈에 넣지 않는다. 후속 승인 뒤 `prompts/`에 버전으로 둔다.

## 7. 검증 순서와 수용 기준

1. `python -m unittest discover -s tests` 통과.
2. `parse` 실행 후 `parse_report.json`이 1.4 수치와 일치.
3. `filter` 실행 후 `candidate_report.md`를 팀에 공유하고 `MANUAL_CHECK` 어휘 목록 보강 여부 결정.
4. `audit-sample`로 시트 생성, 사람 판정, 결과를 `data/interim/audit_result_v1.tsv`로 보존.
5. audit 통과 후 `configs/study.json` 갱신, `split`과 `sample` 실행, manifest 커밋 대상 여부 확인(현재 `.gitignore`는 manifests도 제외한다. 공개 범위는 약정 확인 후 결정).
6. 각 단계의 실행 명령과 seed를 `data/manifests/README.md`가 아니라 `data/manifests/run_log.md`에 날짜와 함께 기록.

검사하지 않은 항목을 통과했다고 쓰지 않는다. 수치는 실제 실행 결과만 적는다.

## 8. 하지 말 것

- 복원형이나 antecedent 위치를 audit 시트, payload, 프롬프트에 노출하는 것.
- `#`에 붙은 sentence_id를 근거 위치로 해석하는 것.
- 문장 ID 문자열을 파싱해 순서를 추정하는 것. 배열 순서를 쓴다.
- speaker-run을 원래 turn이라고 부르는 것. 항상 `speaker_run_proxy`로 표기한다.
- 2024 ZA 구어를 2025와 합치거나 보조 자료로 섞는 것.
- 신문 ZA 파일을 파이프라인에 넣는 것.
- 모델 결과를 본 뒤 후보 풀이나 split을 바꾸는 것.
- 실제 문장, 문서 ID, 화자 ID를 코드·테스트·문서·커밋 메시지에 넣는 것.
